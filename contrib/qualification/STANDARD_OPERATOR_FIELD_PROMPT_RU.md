# Проверка кандидата 0.3.0: Standard operator

Подготовь и выполни в согласованном реальном контуре проверку RDP reconnect
и upgrade/rollback кандидата `0.3.0rc1`. Релиз не публикуй.

## 1. Входные данные и идентичность

Используй переданный закрытым одобренным способом комплект кандидата:

- `enclave_gateway-0.3.0rc1-py3-none-any.whl`.
- `source.tar.gz`.
- `candidate-manifest.json`.
- `SHA256SUMS`.
- `FIELD_VALIDATION_PROMPT_RU.md`, если приложен конкретизированный промпт.

Точный commit кандидата: `{{CANDIDATE_COMMIT}}`.
Ожидаемый SHA-256 wheel: `{{CANDIDATE_WHEEL_SHA256}}`.
Если остались незаполненные placeholders, сначала установи точную идентичность
через независимо проверенный манифест. Не угадывай commit и hash.

Принятый baseline и пакет для отката:

- Version: `0.3.0b7`.
- Tag: `v0.3.0-beta.7`.
- Commit: `bcafbb1ae71bd044ed6ec4a8a0cf7fafbefd7f44`.

  `7b200c5459355d3d262be11ff3e5aa66b67a6c05f52d5870147ccfa4dad48ee8`.

утверждённые hashes. Не меняй pins на непроверенные значения ради запуска.

## 2. Границы и подготовка

Используй существующий одобренный маршрут Standard operator:

- HOST_A.
- QGA и APPLIANCE_A.
- Одобренный VPN.
- RDP drive redirection и BASTION_A.
- Системный OpenSSH.
- Один Linux TARGET_A с forced-command peer.

Ожидаемые настройки:

- `security.mode: standard`.
- `execution_profile: structured_only`.
- `structured_backend: operator`.
- `spool_protocol: stream`.
- Свежая worker attestation включена.
- Существующие policy и pins сохранены.

Зафиксируй фактическую версию KES. Предыдущая приёмка относилась к
`21.3.10.1001`. Не объявляй другую версию уже принятой.

Не изменяй код продукта или агентов. Не ослабляй KES и другие политики.
Не меняй ACL или execution policy. Не удаляй transaction tombstones.
Не перезапускай QGA или ВМ для имитации RDP reconnect.

Используй согласованное окно и отдельные синтетические файлы. Убедись, что
разрываемый RDP-клиент принадлежит испытанию. Сохрани независимый способ доступа
для наблюдения и восстановления. Не закрывай чужие RDP-сеансы.

Создай новый закрытый каталог доказательств. Сохраняй все неудачные попытки.
До смены пакета проверь baseline Beta 7:

```sh
<EGW> --version
<EGW> -c <PRIVATE_CONFIG> config check
<EGW> -c <PRIVATE_CONFIG> doctor --preflight
<EGW> -c <PRIVATE_CONFIG> agent-verify --wait-ready 60
```

Все обозначения в угловых скобках замени локально. В итоговый отчёт их реальные
значения не включай. Используй один и тот же рабочий интерпретатор и launcher.
Проверь путь импорта и package metadata без PYTHONPATH и editable checkout.

## 3. Сохранение состояния перед upgrade

Зафиксируй существующее местоположение конфигурации и Host transaction journal.
Если используется `--state-dir`, сохраняй его во всех связанных вызовах.
Не подменяй рабочий журнал новым пустым namespace для получения успеха.

Останови свой тестовый воркер штатно:

```sh
<EGW> -c <PRIVATE_CONFIG> agents stop --timeout 60
```

Подтверди свежий `stopped` и освобождение lease. Одного acknowledgement мало.
При `worker_stop_pending` не начинай замену до подтверждённого завершения.

Сохрани приватно:

- Конфигурацию с её исходными разрешениями.
- Одобренные policy и pins.
- Host journal через согласованный SQLite backup API либо корректный offline backup.
- Durable worker ledger.
- Незавершённые операции и их доказательства.
- Проверенный wheel Beta 7.

Не копируй один SQLite-файл из активно используемой WAL-базы без согласованного
backup. Не откатывай журнал на старую копию после новых операций: это уничтожает
историю защиты от повтора.

## 4. Upgrade Beta 7 → RC

Установи точный локальный wheel в то же рабочее Host-окружение:

```sh
<PYTHON> -m pip install --no-index --no-deps --upgrade <RC_WHEEL>
```

Зафиксируй результат установки. Подтверди `0.3.0rc1` одновременно через CLI
и importlib.metadata. Проверь 65 файлов по exact-source дереву кандидата.
Перезапусти собственные долгоживущие Host-процессы, которые могли держать старые
импорты. Не меняй конфигурацию или journal namespace.

Конфигурация должна читаться без миграции. Проверь, что старые transaction IDs
доступны. Если нужна неожиданная миграция, сохрани ошибку и останови upgrade.

Байты агентов не меняются: не выполняй произвольное restaging. Проверь deployed
hashes. При необходимости штатной доставки используй только проверенные байты
через прежний одобренный порядок. Запусти foreground worker явно в той же
согласованной RDP-сессии и получи новую свежую attestation.

Выполни candidate smoke:

- `config check`.
- `agent-verify --wait-ready 60`.
- Безопасную команду на TARGET_A.
- Один `heal` с `APPLIANCE_INIT_OK` и `SESSION_ACTIVE`.
- Подтверждение успешного QGA clock sync и `HostEpochUtcMs 0` при init.
- Проверку отсутствия отката часов Appliance с учётом RTT измерения.
- Сохранение worker instance во время heal.
- Round trip нового несжимаемого файла 1 МиБ.
- Независимое совпадение размеров и трёх SHA-256.

Для копирования используй CLI:

```sh
<EGW> -c <PRIVATE_CONFIG> cp --chunked --timeout 1800 <HOST_FILE> <TARGET_ALIAS>:<TARGET_FILE>
<EGW> -c <PRIVATE_CONFIG> cp --chunked --timeout 1800 <TARGET_ALIAS>:<TARGET_FILE> <RETURNED_FILE>
```

MCP `node_transfer` не предоставляет эквивалентного chunked-copy интерфейса.
Не добавляй в MCP-запрос неподдерживаемые параметры.

## 5. Реальный RDP reconnect на RC

Это проверка foreground operator. Она не требует фонового supervisor/autostart.
Если действует иной профиль, не смешивай его результаты с этой приёмкой.

Подготовь две операции с разными уникальными transaction IDs:

- COMPLETED_A: успешная тестовая команда с одним счётным побочным эффектом.
- INTERRUPTED_A: ограниченная тестовая команда с наблюдаемым началом и задержкой.

Используй отдельные marker-файлы на TARGET_A. Счётчики должны позволять независимо
доказать число выполнений. Payload и аргументы каждой операции сохраняй
неизменными при проверке её ID. Не используй операции с рабочими данными.

COMPLETED_A заверши до разрыва. Для INTERRUPTED_A сначала независимо подтверди
достижение контролируемой точки выполнения. Затем действительно отключи только
принадлежащий испытанию native RDP-клиент между Appliance и Bastion.
Исключение в Python или отключение Host ↔ QGA не заменяет этот сценарий.

Сохрани:

- Время разрыва и последующего подключения.
- Windows LocalSessionManager events 24 и 25 для одной и той же сессии.
- Старый worker instance и его фактическое состояние.
- Исходный deadline и результат Host-команды.
- Host journal и durable worker ledger.
- Наблюдаемый эффект на TARGET_A.

После разрыва не повторяй mutating-команду автоматически. Дождись её исходного
deadline. Допустимый исход после dispatch может быть indeterminate. Он должен
оставаться явным до сверки фактического эффекта.

Восстанови тот же RDP-сеанс штатным native-клиентом. Подтверди возврат redirected
drive. Старый worker не должен самопроизвольно перезапуститься. Перед новым
ручным запуском подтверди выход старого foreground worker и свободный lease.
Если старый worker остаётся активным, не создавай второй: зафиксируй состояние
и действуй по штатной процедуре остановки. Не скрывай это как успешный reconnect.

Явно запусти новый экземпляр и выполни fresh attestation. Проверь новый instance.
Сверь фактический эффект INTERRUPTED_A до любой повторной отправки.

Докажи защиту от повтора на двух уровнях:

- Через обычный CLI повторное обращение к прежним IDs использует сохранённое
  состояние Host и не исполняет команды заново.
- Через отдельный ограниченный диагностический harness проверь durable worker
  ledger для тех же завершённого и прерванного IDs после нового attachment.
  Одного возврата из Host cache для этого недостаточно.

Harness использует штатный контракт установленного runtime. Он не меняет
агентов и не удаляет журналы. Намеренное повторное предъявление прежнего ID
должно быть отвергнуто либо вернуть сохранённый исход без нового эффекта.
Не путай этот отрицательный тест с разрешением автоматически повторять работу.

Если cancellation marker мешает отдельной проверке ledger, удаление допустимо
только для собственного тестового marker после сохранения доказательств
и подтверждения выхода старого worker. Ledger и tombstones не удаляй.

Проверь отдельную безопасную новую команду и свежую attestation после reconnect.
Зафиксируй число side effects для обеих операций. Если запуск INTERRUPTED_A был
доказан до разрыва, ожидается ровно одно выполнение. Недостаточное наблюдение
не считается доказательством отсутствия повтора.

Дополнительно прерви тестовую chunked-передачу на границе реально наблюдаемого
частичного прогресса, если это входит в согласованное окно. Не продолжай её
повторной mutating-отправкой без сверки. Отметь этот дополнительный сценарий
отдельно от обязательного command reconnect.

## 6. Rollback RC → Beta 7

Сначала штатно останови worker с подтверждённым освобождением lease.
Сохрани результаты RC и текущие журналы. Не восстанавливай устаревшую backup-базу.

В том же Host-окружении установи проверенный baseline:

```sh
<PYTHON> -m pip install --no-index --no-deps --force-reinstall <BETA7_WHEEL>
```

Подтверди `0.3.0b7` через CLI и package metadata. Сравни установленный runtime
с baseline. Перезапусти собственные Host-процессы со старыми импортами.

Проверь:

- Конфигурация не изменена неожиданно.
- Независимые pins сохранились.
- Старые IDs и результаты RC доступны из того же Host journal.
- Durable worker ledger не заменён пустым.
- Ни COMPLETED_A, ни INTERRUPTED_A не выполняются повторно после rollback.
- После явного attachment проходят attestation и новая безопасная команда.
- Small-file round trip совпадает по размеру и SHA-256.
- Штатный stop завершает worker и освобождает lease в пределах 60 секунд.

При ошибке совместимости не удаляй состояние ради успешного запуска.
Сохрани точную категорию ошибки и оставь контур в безопасном наблюдаемом состоянии.

## 7. Защита и конечное состояние

Сравни активность KES до и после испытания. Проверь новые события за фактический
интервал. Недоступность журнала не означает ноль событий.

Сохрани journals и unresolved evidence. Удали только собственные синтетические
данные после фиксации результатов. `clean` допускается после подтверждённого stop.
Проверь сохранность nonzero response и transaction ledger.

Оставь Host на принятой Beta 7 после rollback. Тестовый worker оставь остановленным.
Если для рабочего контура отдельно согласован запуск, выполни его явно и укажи
конечный instance псевдонимом. Не оставляй скрытую автозадачу или второй worker.

## 8. Обезличенный отчёт и итог

Начни с одного результата:

- УСПЕХ.
- НУЖНЫ ДОРАБОТКИ.
- ПРОВЕРКА НЕ ЗАВЕРШЕНА.

Приложи таблицы:

- Идентичность baseline и candidate с публичными component hashes.
- Каждый этап upgrade и результат проверки установленного дерева.
- RDP события и сохранение той же Windows-сессии без её реального ID.
- Старый и новый worker как WORKER_A и WORKER_B.
- COMPLETED_A и INTERRUPTED_A с независимо измеренным числом выполнений.
- Отдельные результаты Host-journal и worker-ledger duplicate checks.
- Rollback и доступность накопленных результатов без восстановления старой базы.
- Длительности stop и подтверждение свободного lease.
- Clock smoke с RTT и неопределённостью.
- Small-file round trips.
- Защита до и после.
- Конечное состояние и оставшиеся evidence.

Укажи фактические таймауты и все неудачные попытки. Разделяй прямое наблюдение
и вывод из диагностического harness. Raw receipts остаются приватными.

Исключи из публичного отчёта реальные адреса и домены. Исключи логины и SID.
Исключи частные пути и идентификаторы сеансов. Исключи заполненные конфиги.
Исключи hash приватной policy и идентификатор staging-bundle. Исключи секреты.
Используй HOST_A / APPLIANCE_A / BASTION_A / TARGET_A и стабильные псевдонимы.

УСПЕХ требует завершения обязательных upgrade/reconnect/rollback проверок
с доказанным отсутствием повторного эффекта и сохранением состояния.
Преднамеренно прерванная операция может остаться indeterminate при сохранённом
доказательстве одного выполнения и корректной сверке.

Подтверждённая регрессия означает НУЖНЫ ДОРАБОТКИ даже при незавершённой части
программы. При недостатке доступа или доказательств верни ПРОВЕРКА НЕ ЗАВЕРШЕНА.
Не объявляй весь 0.3.0 стабильным по результату этого одного маршрута.
