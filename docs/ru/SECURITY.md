# Архитектура безопасности и развёртывание Enterprise

[English](../SECURITY.md) · Русский · [Обзор проекта](../../README.ru.md)

## Границы доверия

При разрешённом SSH используйте [явный выбор маршрута](ROUTING.md).
Отключённый Bastion не принимает RDP-операции. Выбор SSH сам по себе не создаёт
гарантий Enterprise-изоляции. Ошибка не разрешает другой транспорт.

Оператор хоста управляет CLI и каналами QGA/QMP. QGA обычно выполняет команды
от имени SYSTEM в Windows-апплаенсе. Воркер на бастионе принимает команды через
каталог обмена (спул) на перенаправленном диске RDP и выполняет их от имени
пользователя RDP-сеанса. SSH даёт доступ под отдельной учётной записью целевого
узла. Защищайте управляющие сокеты, конфигурацию, учётные данные, спул и
материалы релиза, включая их родительские каталоги.

Standard предполагает доверие к оператору, сеансу и всем, кто может писать в
спул. Пространства выполнения PowerShell (Runspace) разделяют процесс, права
доступа к файловой системе и окружение. Маскирование секретов и подтверждение
опасных команд помогают избежать ошибок. Для недоверенного скрипта изоляции
нет. Тайм-аут конвейера PowerShell сам по себе не гарантирует завершения
внешнего процесса или удалённой команды. Выбирайте Standard только там, где
допустима такая модель доверия.

Enterprise требует одновременно подписанных агентов и вспомогательных программ,
доверенных отпечатков сертификатов издателей, фиксированных SHA-256 воркера
и нативной среды выполнения, точного SID учётной записи воркера, свежей
аттестации и запуска процессов и SSH-команд под управлением нативной среды.
Значения `false` и `null` для обязательных требований отклоняются. При отсутствии
нативной среды, нарушении подписи, изменении файлов, несовпадении учётной
записи или недостаточной изоляции операция прекращается. Автоматического
перехода в Standard нет. В Custom требования задаются по отдельности. Для
старых конфигураций без `security.mode` действуют прежние значения Custom.

Если политика допускает выполнение подписанных скриптов в общем процессе,
можно использовать Standard с `require_signed_agents: true`, утверждённым
`agent_package_dir`, хешами обоих скриптов и доверенными отпечатками издателей.
Этот вариант позволяет соблюдать требования к подписи скриптов без установки
нативных программ и сохраняет модель доверия Standard.

Нативная среда завершает управляемое локальное дерево процессов при истечении
срока, отмене или завершении супервизора. Удалённый SSH-узел, база данных или
сервис могли успеть выполнить операцию до разрыва соединения. Прежде чем
повторять операцию с неопределённым исходом, сверьте журнал транзакций
с фактическим состоянием удалённой системы.

## Утверждение релиза на сборочной станции

1. Соберите нативные программы и Python-дистрибутив на утверждённой сборочной
   станции с помощью `scripts/release/build_helper.ps1` и
   `scripts/release/prepare_package.py`. Параметры описаны в справке команд.
   На бастионе достаточно утверждённых бинарных файлов среды выполнения.
2. Подпишите пакет с помощью `scripts/release/sign_windows.ps1`, используя
   корпоративный сертификат или сервис подписи кода. Проверьте Authenticode
   и подписанный CMS-манифест через `scripts/release/verify_windows.ps1`.
   Задайте ожидаемого издателя по независимому источнику. Администратор отвечает
   за производственную цепочку доверия, отзыв и ротацию сертификатов и доверие
   к службе меток времени. Временный самоподписанный сертификат подходит для
   испытаний в пределах стенда.
3. Установите соответствующий проверенный пакет на каждом Windows-звене, где
   он выполняется. `scripts/release/install_windows.ps1` проверяет порядок
   выпуска по аутентифицированным данным. Используйте утверждённую процедуру
   обновления Enterprise и сохраняйте защиту от отката.
4. Возьмите за основу `config/enclave.enterprise.example.yaml`. Задайте точные
   утверждённые хеши воркера, bootstrap и нативной среды, отпечатки сертификатов
   и SID пользователя RDP, от имени которого работает воркер. Укажите локально
   проверенный подписанный пакет в `agent_package_dir`. Получайте хеши из
   утверждённого пакета по доверенному каналу.
5. Выполните `egw config check`, `egw doctor --preflight` и `egw agents stage`.
   Перед публикацией неизменяемого бандла staging проверяет хеши воркера и
   bootstrap и их издателей Authenticode на апплаенсе. Установка нативной
   среды и утверждение CMS-релиза выполняются отдельно.
6. Выполните выведенную команду Enterprise bootstrap в выделенном RDP-сеансе на
   бастионе. Bootstrap проверяет подписи и нативную среду до запуска воркера.
   `egw doctor --probe-targets` требует свежих подтверждений релиза, среды и
   SID, затем проверяет рабочий канал. Пульс в `egw status` показывает, что
   воркер подаёт признаки жизни.

`bastion_bootstrap.ps1 -Mode Enterprise -RegisterStartup` регистрирует
управляемую задачу для утверждённого подписанного воркера этого пользователя.
Заранее подготовьте среду выполнения, доверие к издателям, скрипты и пути
запуска. Управляемая задача требует подписанной нативной изоляции и поддерживает
триггеры входа и переподключения. Ранее настроенные подписанные задачи Custom
также поддерживаются.

Отдельная опция `egw agents stage --persist-autostart` регистрирует запись в
`HKCU\…\Run`, когда оператор выполняет сгенерированную команду на бастионе.
Она поддерживает Standard и Enterprise с требованиями выбранного профиля,
фиксирует содержимое локальных скриптов и исключает повторную миграцию.
Подпись Authenticode сохраняется при копировании bootstrap, а запуск
подписанных скриптов сохраняет `AllSigned`. Запись HKCU Run срабатывает при
входе пользователя. Переподключение и аварийное завершение сами по себе эту запись не запускают. Условия и удаление записи описаны в
[руководстве по автозапуску](../GUIDE.md#per-user-worker-autostart).

В режиме Stream супервизор bootstrap повторяет запуск после распознанного
сбоя канала, если ранее проверенная привязка к локальному журналу остаётся
действительной. Перед каждым перезапуском он заново проверяет байты воркера
и настроенные требования доверия. Миграция и команды при этом не повторяются,
а штатная остановка завершает супервизор. Утрата журнала, изменение привязки
или нарушение политики прекращают восстановление. Старые непустые ответы
и запросы сохраняются для сверки. По восстановлению канала нельзя судить
об исходе прерванной удалённой операции.

Продолжают действовать WDAC, AppLocker, ConstrainedLanguage и доменная
политика выполнения. Если запуск `.exe` запрещён, администратор должен
разрешить нативную среду или выбрать допустимую модель доверия без неё.

## Идентификация, политики и MCP

Локальный MCP через stdio для одного доверенного оператора работает с правами
его учётной записи ОС. Для ограниченной интеграции используйте
`egw mcp --read-only`. Авторизация CLI и HTTP определяется отдельно от поля
`actor` и других текстовых имён в аргументах инструментов.

Для управляемого сервиса Enterprise в режиме чтения задайте `--policy` и
аутентифицированного субъекта. Для Enterprise MCP с операциями изменения
добавьте `--isolation-map`.

```sh
egw -c enclave.yaml mcp --policy access-policy.json --isolation-map isolation-map.json
```

Для каждого субъекта создайте профиль бэкенда и закрытый каталог состояния.
Запускайте каждый бэкенд под выделенной непривилегированной учётной записью
ОС с собственным Windows SID или POSIX UID. Политики должны соответствовать
разрешениям брокера, явно перечислять целевые узлы, ограничивать файловый доступ
частными корневыми каталогами и запрещать выполнение команд и доступ к файлам
контроллера. `PrincipalRouter` проверяет эти условия. Изменяемое имя пользователя
или значение `actor` из запроса не подтверждает личность. Разделяйте учётные
данные бэкендов, доступные для записи диски ВМ, спулы и учётные записи целевых
узлов между взаимно недоверенными субъектами.

Для HTTP используйте `--listen` с явной политикой, токенами аутентификации
субъектов и предусмотренными мерами защиты HTTP. При доступе с другого хоста
используйте утверждённый слой терминации TLS. Публикуйте MCP в сети только
с настроенной аутентификацией. Реализация поддерживает HTTP без состояния
и stdio с согласованием поддерживаемой версии протокола. Возобновление
сеансов SSE и произвольные будущие расширения MCP в этот контракт не входят.

`config/access-policy.example.json` задаёт узкие разрешения преимущественно
на чтение. Расширяйте их после проверки потребностей конкретной роли.
Точные ограничения карты бэкендов и тестовые сценарии описаны в документации
для сопровождающих.

## SSH, секреты и хранение состояния

Оставляйте `StrictHostKeyChecking` включённым и сверяйте отпечатки по независимому
доверенному каналу. SSH-клиент может работать на бастионе, апплаенсе или хосте.
Место хранения ключей зависит от звена, на котором запущен SSH.
[Настройка доверия SSH](../GUIDE.md#ssh-trust)

Base64 только кодирует данные. Нативный askpass исключает передачу пароля
через аргументы команды и временные файлы паролей. Привилегированный доступ
к ОС или процессу остаётся в границе доверия. В Standard при выборе входа
по ключу и отсутствии askpass запасной SSH-пароль из конфигурации не извлекается.
Парольный вход требует утверждённого помощника. Для Custom и Enterprise
действуют их собственные проверки помощника.

Храните секреты в хранилище ОС или закрытом файле окружения с подходящими правами
владельца и ACL. Исключайте секреты из файлов топологии, истории команд,
релизных архивов и Git. Ограничивайте доступ к журналам транзакций и аудита,
задавайте сроки хранения и следите за свободным местом. Идентификаторы
транзакций и сохранённые результаты защищают от непреднамеренного повторного
выполнения. После истечения срока хранения сверяйте итог операции явно.
Публичные шаблоны испытаний поставляются без заполненных манифестов, учётных
данных, ключей, образов ВМ и проприетарных установочных носителей.

## Границы приёмки

Тесты исходников, сгенерированные сценарии, эмулированные гости, временная
подпись и локальная установка подтверждают только проверенные сценарии.
Отдельной проверки требуют доверие к аппаратному TPM, сохранность при физической
потере питания, жизненный цикл производственной PKI и совместимость с конкретными
версиями лицензируемых VPN-клиентов и драйверов. Конечный тест также не гарантирует
отсутствия утечек при неограниченной работе. Доступный TCP-порт сам по себе
не подтверждает работу конкретного VPN-провайдера. Управляемый TPM на нативном
Windows-хосте требует поддерживаемого бэкенда. Исторические отчёты в Git
относятся к своим коммитам. Команды и правила обращения с результатами описаны
в [руководстве по квалификации](../../contrib/qualification/README.md).
При обновлении зависимостей заново проверяйте доверенную цепочку инструментов,
поведение среды выполнения и материалы релиза.

Очистка поколений агентов использует совместно удерживаемые файловые блокировки
воркера и staging и эксклюзивную блокировку обслуживания. Она распознаёт только
неизменённые поколения с подтверждением очистки поддерживаемого формата.
Механизм опирается на семантику совместного доступа к файлам Windows через
перенаправленный диск и на защищённого владельца спула. Устаревший пульс
не подтверждает состояние старого воркера. Его поколения автоматически
не принимаются под управление для удаления. Диагностические снимки собирают
данные из списка разрешённых источников. Перед сохранением и передачей
проверьте сводку снимка.

Воркер запускается из проверенной локальной копии и сохраняет идентификаторы
запросов на бастионе. В спуле хранится привязка к исходному владельцу локального
журнала. Миграция сохраняет отметки об уже обработанных транзакциях. При
утрате привязанного журнала выполнение прекращается. Оператор отвечает за
актуальность резервных копий, согласованный откат снимков и сверку удалённых
эффектов. После миграции спула не запускайте на нём старый воркер. Подсказки
очереди и время пульса не дают полномочий и не заменяют свежую аттестацию
релиза, среды и SID в Enterprise.

Опция запуска с `RemoteSigned` на уровне процесса доступна только для
неподписанного профиля Standard. При действующем `AllSigned` запуск с этой
опцией отклоняется. Групповая политика и правила контроля приложений продолжают
действовать. Локальные копии сохраняют метки зоны Интернета. Для подписанных
профилей используйте утверждённую процедуру подписи. После запуска проверенной
локальной копии исходные поколения staging могут быть очищены независимо от
неё. Файловые блокировки защищают источник во время копирования. Правила
хранения текущего и предыдущих поколений для отката продолжают действовать.

### Опциональный потоковый IPC с подтверждением записи

Выбор Stream меняет формат обмена. Перенаправленный ресурс сам по себе
не аутентифицируется этим протоколом. Сохраняйте закрытые ACL спула, границу
доверия RDP-сеанса и проверки nonce, релиза и SID для аттестации Enterprise.
Files и Stream используют один устойчивый журнал транзакций на бастионе
и абсолютные сроки выполнения запросов. Кадры Stream привязывают ответы
к выбранному экземпляру воркера и хешу релиза. Повреждённые или неполные
кадры запросов отбрасываются без выполнения.

Утрата подтверждения оставляет исход операции неопределённым. Автоматического
повтора команды или перехода на другой протокол нет. Файлы канала ограничены
по размеру и уникальны для экземпляра воркера. Участки файлов, занятые успешно
обработанным запросом и ответом, обнуляются до возврата результата. Данные
прерванных операций сохраняются для закрытой сверки. Воркер держит открытым
дескриптор чтения запросов до выхода. Убедитесь, что он завершился, перед
отключением перенаправленного диска или архивацией файлов канала.

## Корпоративная политика защиты конечных точек

В `0.3.0b1` добавлен отдельный экспериментальный профиль `structured_only`.
Он запускается явно в открытом RDP-сеансе и использует утверждённую политику
бастиона. В режиме `spawn` воркер запускает системный OpenSSH с подписью
Microsoft, а запросы идут по протоколу Files. В режиме `operator` оператор
запускает OpenSSH в том же RDP-сеансе, а хост обменивается запросами с адаптером
через Stream. Переключения между режимами при сбое нет. Адаптер не исполняет
PowerShell из запросов и не регистрирует автозапуск.

В режиме `operator` подписанный адаптер обменивается данными с OpenSSH через
локальные именованные каналы с доступом для SID воркера. OpenSSH проверяет
закреплённый ключ сервера и использует выделенный SSH-ключ с принудительным
запуском [`operator_target.py`](../../src/enclave_gateway/agents/operator_target.py)
на одном Linux-узле. Доступ ограничен правами целевой учётной записи,
включая разрешения на запуск команд. При потоковой загрузке адаптер проверяет
SHA-256 перед отправкой последнего байта, а целевой узел проверяет файл перед
заменой назначения. При потере ответа после отправки сверяйте фактический исход
по журналу и на целевом узле перед повтором.

Это подписанное развёртывание Standard. Его граница доверия включает оператора
RDP, администраторов бастиона и процессы с правом записи в спул. Допуск к
эксплуатации по конкретной корпоративной политике требует отдельной приёмки.
[Руководство по политике конечных точек](../ENDPOINT-POLICY.md)

В универсальном режиме секретные данные передаются отдельно от исходного
PowerShell. Спул остаётся привилегированным каналом с чувствительными данными.
Это не защита от привилегированного чтения памяти процесса. Команды, в которые
пользователь явно вставил секрет, могут оставить его в журналах целевого узла.
Обновление RDP-учётных данных использует нативный API на Appliance.
Установка нативного помощника на Bastion для `structured_only` не требуется.
