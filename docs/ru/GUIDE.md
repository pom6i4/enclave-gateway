# Руководство по Enclave Gateway

[English](../GUIDE.md) · Русский · [Обзор проекта](../../README.ru.md)

До подключения выберите [утверждённый SSH- или RDP-маршрут](ROUTING.md).
`egw config init --route ssh` создаёт конфигурацию без RDP-воркера.
Маршрут по умолчанию — `rdp_vfs`. Ошибки не переключают транспорт.

Практическое руководство по подключению к существующему контуру. Полный справочник по подготовке ВМ, настройке провайдеров и обслуживанию приведён в [английском руководстве](../GUIDE.md). Требования Enterprise и границы доверия описаны в [документации по безопасности](SECURITY.md).

## 1. Установка

Требуется Python 3.10 или новее. В корне клонированного репозитория выполните:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -e .
.venv/bin/egw config init
```

На Windows используйте `.venv\Scripts\python.exe` и `.venv\Scripts\egw.exe`. Команды ниже предполагают, что `egw` доступен в PATH. Подробности см. в [разделе установки](../GUIDE.md#installation).

## 2. Конфигурация и состояние

Заполните созданный `enclave.yaml` по [примеру конфигурации](../../config/enclave.example.yaml). Укажите параметры Windows-апплаенса и его каналов управления, согласованный VPN/RDP-маршрут, пути к спулу и целевые узлы. `provider.type: custom` подходит для VPN-соединения, которым управляют отдельно.

Приоритет поиска конфигурации: `-c` или `--config`, `ENCLAVE_CONFIG`, `./enclave.yaml`, `./config/enclave.yaml`, затем `${XDG_CONFIG_HOME:-~/.config}/enclave-gateway/enclave.yaml`. Если нужен глобальный конфиг, создайте его через `egw config init --global`. Для глобальной конфигурации предпочтительны абсолютные пути.

Каталог состояния можно задать через `--state-dir` или `ENCLAVE_STATE_DIR`. По умолчанию глобальная конфигурация хранит аудит и журнал транзакций в соседней папке `state/`. Ограничьте доступ к ней и к используемому файлу `.env`. Подробности и приоритеты приведены в [справочнике по конфигурации](../GUIDE.md#configuration-discovery-and-private-state).

## 3. Подключение и проверка маршрута

Для этого сценария нужен уже подготовленный апплаенс с QGA и согласованный RDP-сеанс от него до бастиона. На бастионе нужны PowerShell FullLanguage и OpenSSH.

```sh
egw config check
egw doctor --preflight
egw agents stage
```

`config check` показывает действующие настройки безопасности и место запуска SSH. `doctor --preflight` проверяет локальные предпосылки. Для проверки живого маршрута запустите воркер:

1. Откройте RDP-сеанс с перенаправлением диска.
2. В PowerShell **на бастионе** выполните полную команду `start_command`, напечатанную при подготовке пакета. Для Standard оставьте воркер запущенным.
3. Настройте SSH-доверие и проверьте маршрут командами ниже.

Перенаправление `C:` предоставляет RDP-сеансу доступ ко всему тому. Используйте выделенный том для спула, если это допускает политика, и задайте согласованные пути с обеих сторон. [Подробности о перенаправлении](../GUIDE.md#protect-the-redirected-drive)

### Доверие SSH

Для `exec`, `cp` и `sync` ключ входа и проверенный `known_hosts` должны находиться на звене, которое выполняет SSH. Для `via: bastion` это профиль пользователя RDP на бастионе. Для `egw ssh` используется OpenSSH на хосте, поэтому файлы доверия и ключ входа нужны там. Сверяйте отпечаток ключа сервера с администратором по доверенному каналу. [Настройка SSH](../GUIDE.md#ssh-trust)

Для примеров ниже предполагается, что в конфиге определён Linux-узел `app01` и на нём разрешена запись в `/tmp`.

```sh
egw doctor --probe-targets
egw exec app01 'id'
printf 'hello\n' > hello.txt
egw cp hello.txt app01:/tmp/hello.txt
egw cp app01:/tmp/hello.txt hello-returned.txt
```

### OpenSSH с ручным запуском на бастионе

Если политика разрешает запуск системного OpenSSH оператором, используйте
[подписанную конфигурацию Standard](../../config/enclave.structured.example.yaml)
для одного Linux-узла и явно выберите режим:

```yaml
bastion:
  execution_profile: structured_only
  structured_backend: operator
  spool_protocol: stream
```

1. На целевом Linux-узле установите [`operator_target.py`](../../src/enclave_gateway/agents/operator_target.py) в каталог под управлением root. Настройте Python 3.10+ и отдельный SSH-ключ с ограничением `restrict,command="…"` в `authorized_keys`. Принудительная команда должна запускать этот скрипт.
2. На бастионе разместите подписанный `bastion_structured.ps1` и утверждённую политику в каталоге под управлением администратора. Укажите в политике `operator_state_dir` на локальном NTFS с доступом на запись для SID воркера и доверенных администраторов. Сверьте ключ сервера в `known_hosts`.
3. В RDP-сеансе запустите адаптер командой, которую печатает `egw agents command`. Откройте отдельное окно CMD в том же сеансе и выполните команду OpenSSH, напечатанную адаптером.

```sh
egw agent-verify
egw exec app01 'uname -s' --timeout 15
egw cp ./hello.txt app01:/tmp/hello.txt --timeout 15
egw cp app01:/tmp/hello.txt ./hello-returned.txt --timeout 15
```

Общий срок для `exec` и обычного `cp` ограничен 15 секундами, включая свежую
аттестацию. Интерактивный SSH и TCP-прокси в этом режиме недоступны. При
разрыве OpenSSH адаптер завершает работу. Сверьте исход незавершённых операций
перед повторным запуском. [Порядок развёртывания](../ENDPOINT-POLICY.md#operator-openssh-backend)

Для файлов до 512 МиБ используйте `egw cp --chunked --timeout 900`, если
`egw agent-verify` показывает `chunked_copy_slots_v1: true`. Команда передаёт
блоки по 1 МиБ, проверяет SHA-256 каждого блока и заменяет файл назначения
после проверки SHA-256 всего файла. Лимит каждого запроса составляет 15 секунд.
Параметр `--timeout` задаёт срок всей передачи. В сеансе должно хватить времени
на завершение копирования и остановку воркера.

```sh
egw cp --chunked --timeout 900 ./artifact.bin app01:/tmp/artifact.bin
egw cp --chunked --timeout 900 app01:/tmp/artifact.bin ./received.bin
egw agents stop --timeout 15
```

[Ограничения и восстановление после обрыва](../ENDPOINT-POLICY.md#larger-files-with-the-operator-backend)

## 4. Эксплуатация и диагностика

- **`SESSION_PENDING_WORKER`.** Проверьте, что команда запуска выполнена в нужном RDP-сеансе и воркер видит перенаправленный спул. `agents stage` подготавливает файлы. Воркер запускается отдельной командой.
- **Ошибка SSH host key.** Сверьте отпечаток и путь к `known_hosts` на выполняющем звене. При неожиданной смене ключа проверьте причину у администратора.
- **Таймаут после отправки.** Операция могла выполниться. Перед повтором сверяйте транзакцию и её фактические эффекты.
- **Блокировка средством защиты.** Прекратите запросы и сохраните доказательства по [инструкции разбора инцидента](ENDPOINT-INCIDENT.md). При неопределённом исходе не повторяйте команду с новым идентификатором.
- **Медленный RDP-маршрут.** Для коротких команд оцените опциональный `bastion.spool_protocol: stream`. Согласуйте конфигурацию хоста и воркера и измерьте задержку на своём маршруте. [Описание Stream и критерии замера](../GUIDE.md#short-command-latency-over-redirected-drives)

Для наблюдения используйте `egw status` и `egw top`. Команда `egw heal` меняет настройки управляемого апплаенса и может переподключить его RDP-сеанс. Выполняйте её в согласованное окно. [Таблица устранения неполадок](../GUIDE.md#troubleshooting)

### MCP

Локальный клиент можно подключить через stdio:

```sh
egw mcp-config
egw mcp --read-only
```

Первая команда выводит примеры клиентской конфигурации. Вторая запускает сервер только для чтения. Укажите нужный конфиг и каталог состояния в параметрах запуска MCP-клиента. Для HTTP и разграничения прав нескольких пользователей см. [правила развёртывания MCP](SECURITY.md#идентификация-политики-и-mcp).
