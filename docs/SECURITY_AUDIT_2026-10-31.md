Исходные 14 тестов проходили, но не подтверждали безопасность границ доверия и совместимость Windows-ветвей. Исправления внесены локально. Квалификация реальной цепочки Windows Appliance → VPN → RDP → Bastion → TargetNode остаётся отдельной задачей: локальные тесты не заменяют её.

## Сверка протоколов и провайдеров

- **QGA/QMP.** Основание для sync, count, flush, exec-status и UTC ns — [QGA reference](https://www.qemu.org/docs/master/interop/qemu-ga-ref.html); корреляция QMP — [QMP specification](https://www.qemu.org/docs/master/interop/qmp-spec.html). QGA timeout не доказывает остановку guest-exec: стандартного guest-exec-kill здесь нет. После timeout процесс в госте может продолжить работу.
- **RDPdr.** [MS-RDPEFS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpefs/632fe39b-4e85-4e4f-be04-0f39dd9257c0) описывает файловые операции канала, а не гарантированную доставку directory notifications. Поэтому уведомления используются только вместе с повторным опросом и проверкой законченного envelope. Нативные задержки кэша и sharing violations требуют реального RDP-прогона.
- **SOCKS.** Реализован CONNECT subset [RFC 1928](https://www.rfc-editor.org/rfc/rfc1928.html), [SOCKS4](https://www.openssh.org/txt/socks4.protocol), [SOCKS4a](https://www.openssh.org/txt/socks4a.protocol). BIND/UDP не поддерживаются и не объявляются поддержанными. [RFC 1929](https://www.rfc-editor.org/rfc/rfc1929.html) auth не реализована: клиенту только с method 0x02 возвращается 0xFF; предложение 0x00+0x02 позволяет выбрать 0x00. Такой proxy следует оставлять на loopback.
- **HTTP.** CONNECT authority соответствует [RFC 9110 §9.3.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.6); absolute/origin forms — [RFC 9112](https://www.rfc-editor.org/rfc/rfc9112.html). Обычный proxy обслуживает один origin request на connection; для HTTPS нужен CONNECT.
- **OpenSSH.** [Release 8.4](https://www.openssh.org/txt/release-8.4) впервые описывает SSH_ASKPASS_REQUIRE. Для 7.7–8.3 остаётся legacy DISPLAY/no-tty поведение; работа конкретного Windows build и helper не доказана. Настройка всех host keys обязательна. Для distroless без sshd и shell этот способ неприменим. Alpine/BusyBox требуют доступных sh, base64 и одной SHA-256 утилиты.
- **ViPNet Windows 4/5.** Удалено предположение, что Windows поддерживает Linux-подобные `vipnetclient info`/`installkey --psw`, и вымышленный общий Windows binary path. Статус получает явно настроенную службу/адаптер и проверяет сетевую доступность через выбранный интерфейс. [Официальный каталог документации](https://infotecs.ru/downloads/documents/vipnet-client-5/) разделяет Windows и Linux. Архив руководств Windows не был разобран: поддержка ARM64, точные CLI/service names и процедура импорта ключа для конкретной версии остаются **не подтверждены**. ARM64-драйвер другого продукта не доказывает поддержку ViPNet. Импорт DST без проверенного адаптера завершается ошибкой.
- **WireGuard Windows.** [Enterprise documentation](https://git.zx2c4.com/wireguard-windows/about/docs/enterprise.md) подтверждает `wireguard /installtunnelservice`, службу `WireGuardTunnel$<name>` и `wg show`. Статус использует `wg.exe` из установленного WireGuard либо явный путь. Наличие Wintun само по себе не доказывает нужный provider или работающий tunnel.
- **Cisco.** [Secure Client 5.1 CLI guide](https://www.cisco.com/c/en/us/td/docs/security/vpn_client/anyconnect/Cisco-Secure-Client-5/admin/guide/cisco-secure-client-admin-guide-new/customize-secure-client-intro/r_use_the_ac_cli_commands.html) подтверждает `vpncli.exe` и `state`; поиск учитывает Secure Client и прежний AnyConnect path. Проверка проводится в госте, а не на Host.
- **OpenVPN.** [Service wrapper](https://openvpn.net/community-docs/running-openvpn-as-a-windows-service/) и [Interactive Service](https://community.openvpn.net/Pages/OpenVPNInteractiveservice) различаются. Проверяются настраиваемые службы; TAP, Wintun и DCO не считаются взаимозаменяемым признаком tunnel. Поддержка драйвера конкретной архитектуры проверяется по установочному пакету.
- **Континент.** `kontinent`/`custom` используют явно настроенные adapter/service и сетевой probe. [Руководство производителя](https://www.securitycode.net/upload/iblock/455/rz68ud54jkxo28c91rj23xhqx7447j9h/Continent-AP%20-%20Windows%20-%20User%20Guide.pdf) относится к конкретному продукту; общий CLI для АП/АПКШ не предполагается. АПКШ — отдельный сетевой компонент, не универсальный Windows client. Полная версия/архитектура требует стенда и пакета поставки.
- **MCP / JSON-RPC / OpenAPI.** Проверены [JSON-RPC 2.0](https://www.jsonrpc.org/specification), [MCP 2025-03-26 transport](https://modelcontextprotocol.io/specification/2025-03-26/basic/transports), [OpenAPI 3.1.0](https://spec.openapis.org/oas/v3.1.0). Согласуются 2024-11-05 и 2025-03-26; stdio newline — стандарт, Content-Length — совместимое дополнительное framing. HTTP stateless: POST отвечает JSON, GET /mcp возвращает 405, SSE/session/resume не реализованы. Legacy HTTP+SSE версии 2024 не заявляется. `/v1/tools` — схема функций; `/v1/tools/call` — локальный bridge, не замена inference API. Конкретные Open WebUI/Ollama клиенты не запускались.
- **CLM / idle.** [PowerShell CLM](https://devblogs.microsoft.com/powershell/powershell-constrained-language-mode/) запрещает используемые worker методы .NET. Worker явно требует разрешённого политикой FullLanguage-компонента и не обходит WDAC/AppLocker. `SetThreadExecutionState` в исходном worker отсутствовал; [документация Windows](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate) не обещает предотвращать screen saver или GPO RDP disconnect. Это обеспечивается согласованной политикой сессии, не heartbeat-файлом.

## Воспроизводимая проверка

```sh
PYTHONPATH=src python3 -m unittest discover -s tests -v && python3 scripts/verify_hygiene.py
```

Последний подтверждённый локальный прогон: **60 тестов, OK**, hygiene PASS. Python 3.14 на macOS; сокетные тесты запускались вне файловой песочницы с разрешённым loopback. QMP smoke использовал установленный QEMU, `-machine none -S`, без гостевого диска, ОС и сетевого интерфейса. Исходный прогон в песочнице был остановлен из-за запрета bind; он не считается PASS. Для среды без QEMU соответствующий smoke пропускается с явной причиной. Грамматика исходников дополнительно проверяется через AST для Python 3.10; это не замена запуска на 3.10–3.13.

PowerShell здесь не установлен. Нет доказательства запуска Windows scripts, HVF/KVM/WHPX с Windows guest, RDPdr под нагрузкой, VPN-подключения, реального SSH password auth, Windows sshd, установщика или EDR-приёмки. Изменения не развёртывались. Публикация исходников не является эксплуатационной приёмкой.

## Оставшиеся ограничения и дальнейшая квалификация

1. Worker выполняет mux I/O последовательно; connect может занимать до своего deadline. Для большого количества медленных соединений нужен самостоятельный неблокирующий I/O worker и общий fairness scheduler. Текущий предел jobs предотвращает рост очереди, но не доказывает высокую пропускную способность.
2. Нет durable transaction journal, аутентификации envelope и надёжного reconciliation после падения worker между выполнением и публикацией ответа. Spool — доверенная командная граница: доступ на запись равен возможности выполнения команд с правами worker. ACL Appliance/Bastion и RDP drive redirection должны быть проверены до эксплуатации. Полный `C:` следует заменить выделенным spool volume при подготовке образа.
3. Cooperative patch lock предотвращает конфликт взаимодействующих клиентов; некооперирующий внешний writer может изменить файл между hash и replace. При необходимости строгого CAS требуется target-side service с версионированием, либо API хранилища с transactional precondition.
4. `DestructiveCommandGuard` остаётся эвристикой, не sandbox: произвольный интерпретатор может скрыть действие. Устойчивое ограничение достигается отдельной capability policy и удалёнными правами; режим read-only больше не доверяет regex для исполнения arbitrary code.
5. Scrubber не может распознать неизвестные незарегистрированные credentials и произвольные срединные фрагменты секрета. Base64 не является шифрованием; privileged process inspection, crash dumps, spool и audit storage должны входить в модель угроз.
6. Не выполнен 10 000-транзакционный Windows soak с измерением handles/RSS, RDP disconnect/reconnect, disk-full и AppLocker/WDAC. Требуется матрица macOS/Linux/Windows Host × x86_64/ARM64 guest × конкретные provider packages. Нельзя объявлять каждую комбинацию поддержанной по генерации команды.
7. Offline qcow2 snapshot является снимком диска, не всей VM RAM/NVRAM. Для согласованного восстановления нужны versioned disk+NVRAM manifests и проверка выключенного состояния. Backing disk CoW-профиля должен оставаться неизменяемым. Планируемые порты профилей могут пересечься по hash; OS bind остаётся обязательной окончательной проверкой.

## Приоритеты развития

| Сценарий | Конкретное улучшение | Критерий приёмки |
|---|---|---|
| Корпоративный доступ | Per-tool/per-node capabilities, ограничение путей и target CIDR, проверенная identity, отдельные непривилегированные учётные записи | Негативные тесты межпрофильного доступа; отсутствие произвольного exec у read-only principal |
| Удалённый MCP | TLS reverse proxy, обязательная аутентификация, явные allowed origins, лимиты по principal; секрет token через vault/env | DNS rebinding, CORS, slowloris и нагрузочные проверки на реальной точке входа |

| Восстановление | Durable journal с состояниями accepted/running/completed/indeterminate и idempotency policy по операции | Crash injection в каждой границе, отсутствие автоматического повтора неидемпотентных действий |
